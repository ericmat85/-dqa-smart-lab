# 管理員排程與委外驗收

一階審查的「編輯排程」現在可直接開啟自動化排程。一般、委外與複合試驗沿用列表的同一個資料庫規則服務；先預覽，再由人員確認儲存草稿，之後仍需儲存樣品編號、填寫檢核與逐階簽名。

批次中缺少樣品空間 U 的案件會顯示原因，可按「修正此筆設定」返回該欄位，其他已輸入的設定保留。系統不會自行猜測樣品空間。預覽過期後須重新產生安排；結果不確定時仍先查詢，避免重複儲存。

「重新設定」原本會同步換成提交按鈕，瀏覽器可能在同一次點擊繼續提交剛重新顯示的表單。重設與提交現在使用不同的按鈕識別，重設也會取消預設提交行為，因此能停留在設定畫面修改資料。

## 委外完整流程

`database/tests/verify_admin_outsourced_flow.py` 在隔離 PostgreSQL 中，用同一個合成管理員執行以下原生操作，最後回滾：

1. 建立委外草稿、送簽，直屬主管預設為自己。
2. 核准主管簽核，產生並確認自動排程草稿。
3. 儲存三件樣品的手填編號，核准一階與二階。
4. 儲存試驗前準備，確認委外預約，簽名接收。
5. 完成試驗、提交有檔案驗證憑證的報告。
6. 同一管理員完成報告兩階審核、查閱及 PDF 封存，委託狀態為 `CLOSED`、報告為 `ARCHIVED`。

涵蓋 `REAL` 與 `VIRTUAL` 委外案件。真實模式僅在本機測試 fixture 移動時間視窗，狀態仍經原生開始／完成指令；虛擬模式才可用加速器。兩者均不配置內部設備。未完成委外預約、試驗前確認或檔案驗證時，管理員也會被阻擋。

瀏覽器回歸另驗證桌面與手機的一階自動排程入口、批次缺值修正、預覽過期、等待與回應遺失後的防重送。HTTP 測試使用真實 BFF 與合成資料庫邊界；原生資料庫完整流程則直接執行 SQL 函式，不以回傳固定成功狀態代替流程。

這些是隔離環境的驗收結果，不代表已替使用者在共用雲端建立或結案一張委外單，也不代表實體試驗已完成。網站上的既有批次紀錄僅唯讀檢查。
