# E1／E3／E4 無回應修正

使用者回報 E4 `INPUT_TOKEN_LIMIT`、E3 `AI_REPORT_SOURCE_MISMATCH`、E1 `AI_OUTPUT_REJECTED`。操作紀錄確認這些是三種不同的資料與回應問題，不能用模型 health「就緒」取代實際驗證。

## 修正

- **E4／E3 整批來源**：將重複 JSON 欄名改為欄位表與資料列格式，保留全部選取值、列順序、來源數量及引用。沒有截取前幾筆或略過失敗來源。縮短每次重複附帶的固定系統說明，保留相同作業限制。
- **E4 連續問答**：歷史生成文字只作理解問題的提示；按 512 bytes 保留完整最近對話，放不下時明示省略筆數。當前資料來源不因此減少。
- **E3 排程來源**：同時核對實際排程編號（含版本尾碼）及畫面中的待排程資料。預審流程的待審項目需由授權 `preapproval_snapshot` 證明，且尚無有效實際排程；仍保留待審狀態，不偽裝成已預約。未知／跨權限來源仍拒絕。
- **E1 輸出**：在既有結構化合約中要求簡短摘要及重要確認事項，避免預設回覆篇幅耗盡輸出空間；E3 章節也採簡短敘述。模型、金鑰、輸出上限及費用上限沒有調高，回應格式、引用及真實 Provider 證據檢查仍保留。
- **查看既有回應**：近期成功請求新增「查看回應」，透過原操作讀回完整內容與 Trace，不再次生成。歷史回應明確標示依當時來源產生；沿用帳號、權限與操作結果保護。

## 驗證

使用同樣 22 筆目前授權來源，在實際 Python 後端輸入檢核重現舊版 `INPUT_TOKEN_LIMIT`；修正後完整請求估算 7159 bytes，低於既有 8192 上限。跨 Node BFF 與實際 Python provider 實作的測試亦確認整批資料及大量歷史文字不會使此情境超限；測試 Provider 為合成傳輸。

另外使用現有簽章後端、既有 gpt-6-luna 額度進行真實模型驗證：

| 引擎 | 實際來源 | 結果 |
| --- | --- | --- |
| E4 | 同樣 22 筆授權委託 | 成功回答登記數量及資料範圍 |
| E3 | 原失敗選取的 7 筆來源 | 成功整理 5 筆既有排程及 2 筆待審項目，未把待審資料標成已預約 |
| E1 | 同案目前版本及對應試驗目錄、簽名筆數 | 成功回傳三項簡短確認事項，保留未驗證與待補證據 |

真實驗證透過修正後相同的 BFF 組包方式與現有簽章服務，不代登真人帳號，不宣稱已完成真人瀏覽器登入的端到端操作。模型結果核對 Provider 請求／回應、Trace、引用、用量與費用，再讀回原結果；沒有自動重送生成。真實來源與回覆只保存在工作區私人證據，不放入公開儲存庫。
