# 空白委託單上傳範圍誤判修正

使用者的 Excel 範本被「最多 2000 列、48 欄」擋下。原上傳檢查直接使用 ExcelJS 的 `rowCount`／`columnCount`，把沒有內容的儲存格及版面殘留一起算進去。這類檔案即使列印範圍很小，也可能宣告到 CK 欄、XFD 欄或很後面的列。

本次附檔為 29,540 bytes，工作表宣告範圍 A1:CK45（89 欄），實際非空白內容最右到 AQ（43 欄），列印範圍 A1:AR45（44 欄）。原檔未超過實際內容限制，既有預覽程式也已能正確顯示。

上傳驗證現在共用預覽的 `reportBounds` 規則：保留真實內容、列印範圍、有效合併區與圖片位置，不把無內容的格式及列印範圍外空白合併區當成有效內容。上傳仍採 2000 列、48 欄，報告預覽原本的 50 欄限制維持。錯誤會指出工作表名稱與實際範圍。

前端上傳、伺服器 API 驗證、預覽與下載前的重新檢查都使用相同驗證函式。驗證不另存或重新序列化原始 Excel，保存與下載的 bytes 保持一致。檔案大小、ZIP／解壓縮上限、100000 個儲存格、公式、巨集、外部連結、工作區隔離、權限與雜湊檢查維持。

驗證包含：

- 合成範本的 CK 欄／第3000列空白格式，以及列印範圍外空白合併區，可上傳、讀回及預覽；保存原始 bytes。
- 真正位於第49欄或第2001列的內容、過大的列印範圍、有內容的遠端合併區及圖片位置仍拒絕。
- API 接受相同版面問題的合成檔，轉送原始 base64 與雜湊。
- 桌面與手機操作可上傳、預覽45列44欄、下載完全一致的原檔。
- 使用者附檔僅在本機檢查與隔離瀏覽器 API fixture 驗證，不提交檔案內容、不上傳正式資料庫。

本次沒有資料庫遷移、不修改已保存版本、不刪除委託或範本。PR49 維持未合併，只更新受保護的私人預覽。

本次完整899項程式／API測試、28項桌面／手機介面案例及附檔另2項隔離瀏覽器案例均通過；建置、Lint（既有專案警告）與diff檢查通過。詳細結果見 verification.json。
